### Options for Site A (`workflow.py:24` — route classifier)

#### Option 1: `fallback` — Jev Choice with original LLM fallback

**Primitive:** Choice (4 criteria: `billing`, `technical`, `account`, `product`)

**What it does:** Call Jev first with a Choice question over the 4 route options. If confidence exceeds a tuned threshold, use the Jev answer for routing. Below threshold, or on error/timeout, fall back to the original `llm_call` + XML-parse path.

**Reasoning diagnostic:** The original `<reasoning>` printed to stdout must be preserved. On the Jev path, emit a synthetic diagnostic (e.g., `"[Jev routing] Selected: billing (confidence: 0.97)"`) so stdout behavior remains informative. On fallback, the original reasoning prints as before.

**Benefit:** Jev Choice is ~100ms and significantly cheaper than a Sonnet call. For high-confidence tickets (likely most of these clear-cut support tickets), latency drops from seconds to milliseconds. Expected cost = Jev cost + fallback fraction × original cost.

**Risk:** Conservative posture retains fallback, so worst case is Jev latency added before original call on low-confidence inputs. Reasoning diagnostic text changes format on the Jev path (synthetic vs. LLM-generated), but content semantics are preserved. Scope limited to demo fixtures — not validated for adversarial production input.

**Scope:** Add a `decisions.py` module with the Jev question definition. Modify `workflow.py:24` call site to try Jev first, fall back to existing path. Preserve `llm_call` and `extract_xml` unchanged for fallback and Site B.

#### Option 2: `decompose` — Separate routing decision from reasoning generation

**Primitive:** Choice for routing; original LLM for reasoning only when needed

**What it does:** Split the current MIXED call into two independent paths: (1) Jev Choice for the route selection, (2) a separate, cheaper LLM call solely for generating the reasoning diagnostic, only when the Jev path is taken and reasoning diagnostics are desired.

**Benefit:** Cleanly separates the DECISION from the GENERATION. The routing decision gets Jev speed/cost advantages. Reasoning can be made optional or logged at a different level.

**Risk:** Two calls instead of one on the Jev path if reasoning is always generated. More complex code. Changes observable behavior if reasoning generation is skipped or uses a different model. Requires explicit decision about when to generate reasoning.

**Scope:** Larger refactor — new decisions module, modified route function with conditional reasoning call, new prompt for reasoning-only generation.

#### Option 3: `leave` — No conversion

**Primitive:** none

**What it does:** Keep the current implementation unchanged.

**Benefit:** No integration risk. No new dependency. No behavior change.

**Risk:** None — status quo maintained.

**Scope:** No changes.

### Summary

This workflow has **one convertible opportunity** (the route-classification component of Site A) and **one site that must remain as-is** (Site B, pure generation). Site A is MIXED because it produces both a routing decision and printed reasoning; conversion must address the reasoning diagnostic.

**Recommended path:** Option 1 (`fallback`) for Site A is the best fit for conservative risk posture — it captures the Jev cost/latency benefit on the routing decision while preserving the original path as fallback and maintaining observable stdout diagnostics.
